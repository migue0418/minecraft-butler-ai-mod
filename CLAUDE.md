# CLAUDE.md — MinecraftButlerAI

## Project summary

This repository is a Minecraft Java Edition Fabric mod named `MinecraftButlerAI`.

The long-term goal is to create an AI-powered Minecraft butler NPC called **Alfred**. Alfred will eventually be able to receive natural-language instructions from a FastAPI backend, execute safe in-game actions, follow the player, move to positions, inspect/manage chests, and later support voice input/output.

The current goal is **not** the full NPC. The current goal is a small, stable MVP that proves the Java/Fabric side can load, register commands, read server/player state, and execute simple mock actions.

## Current technical context

- Platform: Minecraft Java Edition.
- Mod loader: Fabric.
- Language: Java.
- Build: Gradle + Fabric Loom.
- Runtime target: the version already configured in this repository.
- JDK: use the JDK required by the project Gradle/Fabric setup. Do not downgrade the project unless explicitly requested.

- NPC name: Alfred.
- Mod should compile and run with `./gradlew.bat runClient` on Windows.

## First MVP target

Implement a server-side command system for `/butler`.

Required commands:

### `/butler ping`

Expected behavior:
- Sends a chat/system message to the command source:
  - `Alfred está operativo.`

Purpose:
- Prove the mod loads and command registration works.

### `/butler pos`

Expected behavior:
- Reads the executing player's block position.
- Sends a message:
  - `Tu posición es: X Y Z`

Purpose:
- Prove the mod can read server-side player state.

### `/butler here`

Expected behavior:
- Reads the executing player's block position.
- Stores it in a temporary in-memory state holder.
- Sends:
  - `Posición guardada para Alfred: X Y Z`

Purpose:
- Prove the mod can keep temporary runtime state.

### `/butler target`

Expected behavior:
- If a saved position exists, sends:
  - `Objetivo actual de Alfred: X Y Z`
- If no saved position exists, sends:
  - `No hay posición guardada. Usa /butler here primero.`

Purpose:
- Prove stored state can be read later.

### `/butler mock`

Expected behavior:
- Executes a mock action through a small action executor.
- Sends:
  - `[Alfred] He recibido una acción mock correctamente.`

Purpose:
- Prove the future FastAPI action pipeline shape before networking is added.

## World context collector (implemented)

The mod sends a world snapshot with every request to Alfred (change: `world-context-collector`):

- `WorldContextCollector.collect(player, server)` is called before each HTTP request
- Scans: player inventory, registered chests (real-time BlockEntity read), animals within 30 blocks, crops within 20 blocks (height ±5)
- `WorldContext` is serialized as `world_context` field in `/ask` JSON body and as a multipart form field in `/ask-voice`
- Backend ignores `world_context` until adapted in a separate backend change
- Chest scan skips unloaded chunks silently; crop scan uses `CropBlock.getAge(state)` / `CropBlock.getMaxAge()`
- Only works in singleplayer / LAN for the voice path (same constraint as push-to-talk)

## Voice push-to-talk (implemented)

The mod includes a push-to-talk system (change: `voice-push-to-talk`):

- Hold `V` → records microphone audio via `javax.sound.sampled.TargetDataLine`
- Release `V` → sends WAV to `POST /api/butler/ask-voice` → executes returned `ButlerAction` list
- Max 30s recording; auto-sends if limit reached
- Min 300ms check; shows `[Alfred] Audio demasiado corto.` if too short
- Ignores key press when a UI screen is open
- Uses `KeyMappingHelper.registerKeyMapping()` (Fabric API `fabric-key-mapping-api-v1` 0.149+)
- Uses `KeyMapping.Category.GAMEPLAY` (not the old String category)
- Uses `mc.gui.getChat().addClientSystemMessage()` for client-side chat messages
- Only works in singleplayer / LAN (integrated server). Dedicated server requires network packets (future phase).

## Recommended implementation approach

### 1. Register commands

Use Fabric's command registration API.

Expected pattern:
- Register commands from the main `ModInitializer`.
- Use `CommandRegistrationCallback`.
- Use Minecraft's Brigadier command tree.
- Use server-side command source/player types appropriate for the configured Minecraft version.

If imports differ because of Minecraft/Fabric version mappings, inspect the generated code and dependencies rather than guessing.

### 2. Temporary state

Create a simple static in-memory state class for the MVP.

Example responsibility:
- Store one `BlockPos savedPosition`.
- Provide:
  - `setSavedPosition(BlockPos pos)`
  - `getSavedPosition()`
  - `hasSavedPosition()`

This does not need persistence.

### 3. Mock action executor

Create a tiny action model and executor.

Example model:

```java
public record ButlerAction(String type, String message) {}
```

Example executor:
- `speak` action sends `[Alfred] <message>` to the player.
- Unknown actions return a clear message and do nothing dangerous.

This will later become the bridge from FastAPI action plans.

## Safety rules

Never implement anything that lets an LLM or external backend execute arbitrary Minecraft commands.

Allowed action style:

```json
{
  "type": "speak",
  "message": "Hola"
}
```

Forbidden action style:

```json
{
  "command": "/op player"
}
```

The Java mod must always validate actions locally before executing them.
